============================================================
PHASE 2: CHUNKED SIMULATION (POST-OPTIMIZATION)
============================================================

Objective:
Reduce temporary memory allocations and improve execution time
without changing the mathematical simulation model.

Implementation:

The simulation workload was divided into smaller batches.

Instead of generating random shocks for every simulation at once,
the implementation now:

1. Allocates the final output array.
2. Generates random shocks for one chunk.
3. Applies Cholesky correlation.
4. Calculates GBM increments.
5. Performs cumulative summation and exponentiation.
6. Stores the resulting paths in the corresponding output slice.
7. Releases temporary arrays before processing the next chunk.

Initial default chunk size: 10,000

WHY SMALLER CHUNKS?

The simulation needs temporary arrays to hold random shocks,
correlated shocks and cumulative increments.

Larger chunks process more simulations simultaneously.
Consequently, their temporary arrays consume more memory.

Smaller chunks reduce the size of these temporary arrays.

However, smaller chunks also introduce more loop iterations
and repeated processing overhead.

Therefore, smaller chunks do not necessarily guarantee faster
execution.

In the latest experiment, chunk size 1,000 had both the lowest
runtime and lowest peak traced memory.

The difference in runtime was relatively small, so the result
should not be interpreted as a universal performance guarantee.

Decision:

Use 1,000 as the current default chunk size.

Configuration location:
config.py

DEFAULT_CHUNK_SIZE = 1_000

The value can be adjusted depending on available memory,
hardware and simulation workload.

WHY AND HOW DOES SCALING WORK?

The simulation output has dimensions:

(number of simulations,
 number of time steps + 1,
 number of assets)

For float64 values, each element occupies 8 bytes.

Approximate output memory:

M = 8 × N × (T + 1) × A

Where:

N = Number of simulations
T = Number of time steps
A = Number of assets

This explains the observed behaviour.

Doubling the number of assets approximately doubles memory.

Doubling the number of time steps approximately doubles memory.

Doubling both approximately quadruples memory.

Runtime also increases as the number of simulated values
and calculations increases.

The measured runtime is not perfectly linear because of
matrix operations, memory allocation, CPU behaviour and
other implementation overhead.

Important distinction:

Chunking reduces temporary working memory, but does not
eliminate the memory required to store the complete output.

The final paths array remains the dominant memory requirement
at larger workloads.


============================================================
PHASE 5: CURRENT CONCLUSIONS
============================================================

1. The original implementation had substantial temporary
   memory allocation overhead.

2. Chunking significantly reduced peak traced memory.

3. Runtime improved considerably at larger simulation counts.

4. A chunk size of 1,000 is the current configuration choice.

5. Memory scales approximately linearly with simulation count,
   number of assets and number of time steps.

6. The full output array remains a major memory constraint.

7. The seeded simulation results remained consistent across
   chunk sizes and before/after optimization in the baseline
   comparisons.


============================================================
NEXT ENGINEERING MILESTONE
============================================================

Memory-Efficient Simulation Output

Current limitation:
simulate_gbm() returns and retains the entire price-path matrix.

Potential improvements:

1. Terminal-value-only simulation:
   Calculate terminal prices without retaining every
   intermediate time step.

2. Streaming simulation:
   Generate chunks and pass them to downstream calculations
   without retaining all paths.

3. Online statistics:
   Calculate means, variances and other statistics incrementally.

4. Risk aggregation:
   Compute portfolio terminal values and risk metrics
   without requiring the complete asset-price path matrix.

The objective is to support larger simulation workloads
without requiring memory proportional to the entire
simulation trajectory matrix.
